# Архитектура многомодельной разработки

Версия 1.1. Документ не привязан к конкретным моделям: роли описаны через обязанности, модели — взаимозаменяемые исполнители (см. раздел 9).

---

## 1. Назначение и принципы

Система распределяет работу над проектом между человеком и несколькими ИИ-моделями с разной стоимостью, качеством и лимитами.

**Принципы:**

1. **Человек принимает решения, модели исполняют.** Ни одна модель не меняет цели, приоритеты, scope, VISION и SCOPE. Bridge только предлагает правки.
2. **Источник правды — репозиторий, а не чаты.** Контекст живёт в файлах (`docs/PLAN.md`, `docs/tasks/*`, `AGENTS.md`, `VISION.md`, `SCOPE.md`). Любую модель можно заменить без потери контекста.
3. **Думать дорого, исполнять дёшево.** Дорогие и ограниченные ресурсы тратятся на планирование и приёмку, дешёвые — на исполнение.
4. **Контракты вместо вольных пересказов.** Все передачи между ролями идут в фиксированных форматах (раздел 6).
5. **Проверка автоматизирована, где возможно.** Приёмка человека — последний барьер, а не единственный.
6. **Минимальный дифф.** Исполнитель меняет только то, что указано в ТЗ.
7. **Деградация без остановки.** Потеря любой модели заменяется по таблице из раздела 9.

## 2. Роли

### 2.1 Lead (человек)

| | |
|---|---|
| Задача | Цели, приоритеты, приёмка, решение «мержить или нет» |
| Вход | Идея, запрос, обратная связь по результатам |
| Выход | Утверждённый план, принятые или отклонённые задачи |
| Не делает | Рутинный код, написание ТЗ вручную с нуля (делегирует Bridge) |
| Инструкция | `roles/01-lead-human.md` |

### 2.2 Bridge (Claude)

| | |
|---|---|
| Задача | Превращает цели в декомпозицию и ТЗ, решает, кому делегировать, принимает неоднозначное, ревьюит критичные диффы |
| Вход | Цели от Lead, `docs/VISION.md`, `docs/SCOPE.md`, состояние `docs/PLAN.md`, отчёты исполнителей |
| Выход | Обновлённый план, ТЗ по шаблону, вердикт ревью |
| Не делает | Не пишет большие объёмы кода и не берёт рутину (расходует ограниченную квоту) |
| Инструкция | `roles/02-claude-bridge.md` |

### 2.3 Routine (Gemini, чат)

| | |
|---|---|
| Задача | Однозначные локальные задачи, дёшево проверяемые: шаблонный код, тестовые данные, регулярки, документация, commit-сообщения, суммаризация, перевод, одиночные скрипты |
| Вход | ТЗ в стандартном формате + нужные файлы целиком |
| Выход | Результат строго в запрошенном формате, без лишнего текста |
| Не делает | Архитектурные решения, многофайловые изменения, задачи без критерия проверки |
| Инструкция | `roles/03-gemini-routine.md` |

### 2.4 Executor (агент в IDE)

| | |
|---|---|
| Задача | Пишет код в репозитории по готовому ТЗ на 1–3 файла |
| Вход | Файл `docs/tasks/T-XXX.md` + постоянные инструкции проекта |
| Выход | Изменения в коде и короткий отчёт по формату (раздел 6.3) |
| Не делает | Не планирует, не рефакторит вне scope, не ставит зависимости, не запускает проверки без разрешения |
| Инструкция | `roles/04-agent-executor.md` (копируется в `AGENTS.md` и `.github/copilot-instructions.md`) |

## 3. Источник правды

Файлы в репозитории, которые читают все роли:

| Файл | Содержимое | Кто пишет | Кто читает |
|---|---|---|---|
| `docs/VISION.md` | Зачем проект, цели, критерии успеха | Lead | Bridge, Lead |
| `docs/SCOPE.md` | Что входит в релиз, что нет, ограничения | Lead | Bridge, Lead |
| `docs/PLAN.md` | Цели, этапы, список задач, статусы | Bridge (по решению Lead) | Все |
| `docs/tasks/T-XXX.md` | ТЗ одной задачи | Bridge | Исполнитель |
| `docs/DECISIONS.md` | Принятые архитектурные решения и причины | Bridge, Lead | Все |
| `docs/ACCEPTANCE.md` | Чек-лист приёмки | Lead (один раз) | Lead, Bridge |
| `AGENTS.md` | Правила для агентов | Lead | Агенты |
| `.github/copilot-instructions.md` | То же для Copilot | Lead | Copilot |

Исполнители VISION и SCOPE не читают: им хватает ТЗ. 
Чаты — рабочая поверхность, не хранилище. Вывод из чата, который важен, переносится в файл.

## 4. Жизненный цикл задачи

```
Lead: цель
   │
   ▼
Bridge: уточнение (≤2 вопросов) ──► обновляет PLAN.md
   │
   ▼
Bridge: декомпозиция на задачи T-XXX, для каждой — маршрут (Routine или Executor)
   │
   ▼
Lead: утверждает план (одним «ок» или правками)
   │
   ├──► Routine: ТЗ в чат ──► результат ──┐
   │                                      │
   └──► Executor: T-XXX.md ──► код+отчёт ─┤
                                          ▼
                              Автопроверки (тесты, линтер, типы)
                                          │ прошли
                                          ▼
                              Lead: проверка диффа по ACCEPTANCE.md
                                          │ критично?
                                          ├─ да ──► Bridge: ревью диффа (баги и риски)
                                          ▼
                                    Коммит, статус в PLAN.md
```

**Стадии:**

1. **Intake.** Lead формулирует цель. Bridge задаёт не более двух ключевых вопросов, если цель неоднозначна. Bridge сверяет любую новую цель с «Не входит в РЕЛИЗ». Если запрос туда попадает, он говорит об этом, а не планирует.
2. **Plan.** Bridge обновляет `PLAN.md`: этап, список задач, зависимости.
3. **Decompose.** Каждая задача получает размер (S/M/L) и маршрут. L-задачи делятся дальше.
4. **Delegate.** Bridge выдаёт ТЗ по шаблону. Для Executor ТЗ сохраняется файлом.
5. **Execute.** Исполнитель работает строго в рамках ТЗ.
6. **Verify.** Автопроверки запускает Lead (не агент).
7. **Accept.** Lead проверяет дифф по чек-листу. Критичные места уходят на ревью к Bridge.
8. **Close.** Коммит, статус в `PLAN.md`, при необходимости запись в `DECISIONS.md`.

## 5. Правила делегирования

### 5.1 Дерево решения

```
Задача однозначна?
├─ нет ──► остаётся у Lead/Bridge (решение, уточнение)
└─ да
    Есть проверяемый критерий готовности?
    ├─ нет ──► Bridge дописывает критерий или задача остаётся у Bridge
    └─ да
        Затрагивает репозиторий (1–3 файла, нужен контекст проекта)?
        ├─ да ──► Executor
        └─ нет ──► Routine
```

### 5.2 Матрица

| Тип задачи | Маршрут |
|---|---|
| Архитектура, выбор технологий, компромиссы | Lead + Bridge |
| Декомпозиция, ТЗ, приоритизация | Bridge |
| Ревью критичного диффа (безопасность, данные, деньги) | Bridge |
| Правка или новая функция в 1–3 файлах | Executor |
| Тесты для готовой функции | Executor (если нужен контекст репо) или Routine |
| Шаблонный код, CRUD по образцу | Routine или Executor |
| Тестовые данные, фикстуры, моки | Routine |
| Регулярки, SQL-запросы, одиночные скрипты | Routine |
| README, комментарии, commit-сообщения, changelog | Routine |
| Суммаризация логов и документации, перевод | Routine |
| Многофайловый рефакторинг | Разбить на шаги по ≤3 файлов, каждый шаг — Executor |
| Отладка непонятного бага | Bridge (гипотезы) → Executor (точечная правка) |

### 5.3 Размер задачи

| Размер | Признак | Действие |
|---|---|---|
| S | 1 файл, понятный результат | Делегировать сразу |
| M | 2–3 файла | Делегировать с подробным ТЗ |
| L | >3 файлов или нужны решения | Разбить, прежде чем делегировать |

## 6. Контракты

### 6.1 ТЗ

```
ID: T-XXX
Цель: <1 предложение>
Контекст: <ссылки на файлы/решения, только необходимое>
Файлы: <пути: изменить/создать>
Делать:
1. ...
2. ...
Не трогать: <что вне scope>
Готово, когда: <проверяемые критерии>
Как проверить: <команда или ручной сценарий>
Формат ответа: <дифф | фрагмент + куда вставить | файл целиком>
```

Шаблон-файл: `skeleton/docs/tasks/_TEMPLATE.md`.

### 6.2 Правило неоднозначности

Исполнитель при неясности **задаёт один вопрос и останавливается**. Он не выбирает вариант сам.

### 6.3 Отчёт исполнителя

```
Изменено: <файл — что именно, 1 строка на файл>
Не сделано: <если что-то из ТЗ не выполнено, и почему>
Проверить: <команда/сценарий>
Вопросы: <если есть>
```

### 6.4 Вердикт ревью (Bridge)

```
Вердикт: принять | принять с правками | отклонить
Баги: <список или «нет»>
Риски: <список или «нет»>
Лишнее в диффе: <список или «нет»>
```

## 7. Приёмка (quality gates)

Порядок строгий, каждый шаг дешевле следующего:

1. **Автоматические проверки:** сборка, типы, линтер, тесты. Запускает Lead.
2. **Проверка scope:** в диффе нет файлов вне ТЗ, нет новых зависимостей, нет переименований и форматирования «заодно».
3. **Соответствие критериям «Готово, когда».**
4. **Ревью Bridge** только для критичных мест: безопасность, работа с данными, деньги, публичные API, миграции.
5. **Решение Lead.**

Отклонённая задача возвращается с конкретной причиной в виде правки ТЗ, а не вольным «переделай».

### Приёмка релиза
1. Критерии успеха релиза из `VISION.md` выполнены.
2. Все задачи релиза в статусе `done`.
3. README и `DECISIONS.md` актуальны.
4. Запись в девлоге или changelog, тег версии.
5. Ретроспектива проведена, новые строки внесены в `roles/`.

## 8. Управление квотами

| Ресурс | Особенность | Правило |
|---|---|---|
| Bridge (free-лимит) | Мало сообщений | Только планирование, ТЗ, ревью. Не исполнять |
| Routine (подписка) | Большой запас, много лишнего текста | Основной объём рутины. Жёсткий формат ответа |
| Executor (кредиты по токенам) | Расход растёт с контекстом и циклами агента | Одна задача — один чат. Только нужные файлы. План до действий. Без самостоятельного запуска тестов |
| Автокомплит IDE | Не расходует кредиты агента | Использовать постоянно для рутины при наборе |

**Если кредиты Executor кончились:** задача уходит в Routine по запасной схеме (раздел 9), файлы передаются целиком.

## 9. Отказоустойчивость

### 9.1 Таблица замен

| Потерян | Замена | Что меняется |
|---|---|---|
| Bridge (Claude) | Любая сильная модель с хорошим рассуждением; `roles/02` вставляется как системная инструкция | Ничего, кроме качества декомпозиции |
| Routine (Gemini) | Любая модель, `roles/03` как системная инструкция | Возможно больше правок формата |
| Executor (Copilot agent) | Routine в чате: ТЗ + файлы целиком, ответ фрагментами с указанием места вставки | Больше ручной вставки |
| Весь ИИ | Lead работает по `PLAN.md` и ТЗ сам; шаблоны остаются полезны как чек-листы | Скорость |
| Любая модель, любая роль | `roles/05-fallback-any-model.md` — универсальная инструкция на одну страницу | — |

### 9.2 Что делает схему переносимой

- Инструкции ролей лежат в файлах, а не в настройках конкретного сервиса.
- Контекст проекта лежит в репозитории.
- Форматы ТЗ и отчётов не зависят от модели.

## 10. Типовые сбои и защиты

| Сбой | Защита |
|---|---|
| «Испорченный телефон» между моделями | Контекст берётся из файлов, а не пересказывается |
| Агент делает больше, чем просили | Блок запретов в инструкциях + проверка scope на приёмке |
| Routine пишет лишнее | Жёсткий формат ответа, правило «только результат» |
| Lead перегружен приёмкой | Автопроверки до человека, ревью Bridge только для критичного |
| Квота Bridge кончилась | Задачи заранее разложены в `PLAN.md`, Bridge нужен только для новых решений |
| Задача не проверяется автоматически | Не делегировать Routine; оставить Bridge или Lead |
| Агент зациклился | Остановить, сузить ТЗ, начать новый чат |
| Потеряна история чата | Ничего страшного: состояние в `PLAN.md` и `tasks/` |

## 11. Метрики и ретроспектива

Простые счётчики в `PLAN.md` (в конце каждого релиза):

- Доля задач, принятых с первого раза, по исполнителям.
- Типы правок, которые повторяются (формат, scope, логика).
- Число задач, ушедших в откат.

Из повторяющихся правок рождаются новые строки в инструкциях ролей. Это основной способ улучшать систему.

## 13. Запуск нового проекта

1. Запустить `bootstrap.sh /путь/к/проекту`.
2. Описать `docs/VISION.md` и `docs/SCOPE.md`.
3. Заполнить в `docs/PLAN.md` цель и стек.
4. Дописать в `AGENTS.md` блок «Проект»: структура папок, команды сборки и тестов, соглашения.
5. Вставить `roles/02` в инструкции проекта у Bridge, `roles/03` у Routine.
6. Дать Bridge цель, получить план, утвердить, начать выдавать задачи.
